<Topic 
  id="load-balancers" 
  title="1. Load Balancers" 
  shortDesc="The traffic cop that distributes incoming requests across multiple servers."
>
The traffic cop of your infrastructure, dynamically distributing incoming network traffic across a group of backend servers.

**The Concept**

- **High Availability:** Prevents any single server from becoming a bottleneck. If Server A crashes, the load balancer detects the failure via Health Checks and automatically routes traffic to Server B.
- **Layer 4 vs Layer 7:** Layer 4 (Network) routes based on IP and TCP ports (super fast, low overhead). Layer 7 (Application) routes based on HTTP headers, cookies, or URL paths (smarter, context-aware routing).

**Common Algorithms**

- **Round Robin:** Distributes requests sequentially (A, B, C, A, B, C).
- **Least Connections:** Sends the request to the server with the fewest active connections, which is excellent for long-lived tasks or uneven workloads.
</Topic>

<Topic 
  id="logger-architecture" 
  title="2. Logger Architecture & Observability" 
  shortDesc="Centralized logging, tracing, and metrics for distributed systems."
>
In a distributed system, simply writing `print("error")` to a terminal is useless. You need centralized observability to figure out what went wrong across dozens of servers.

**The Core Pillars**

- **Structured Logging:** Logs must be emitted as JSON, not plain text. This allows you to easily search, filter, and alert on specific machine-readable fields (e.g., `{"level": "ERROR", "user_id": 123}`).
- **Centralized Aggregation:** All services send their logs to a central system (like the ELK Stack, Datadog, or CloudWatch) so you can query everything in one dashboard without SSHing into individual servers.
- **Correlation IDs:** A unique ID generated when a request first hits the API Gateway. This ID is passed to every microservice in the chain. If a request fails deep in the system, you can search the Correlation ID and trace the exact path the request took.
</Topic>
