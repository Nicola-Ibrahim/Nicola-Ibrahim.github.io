# System Design

## Functional vs Non-Functional Requirements

Separating functional requirements from quality requirements helps frame an architecture discussion: what the system must do, and what conditions it must meet while doing it.


| Feature | Functional (The "What") | Non-Functional (The "How") |
| --- | --- | --- |
| **Focus** | Business rules, user actions | Scalability, reliability, latency |
| **Example** | "User can checkout" | "Checkout takes < 200ms" |
| **Missed?** | The app doesn't *work* | The app doesn't *scale* |


### Functional Requirements

These define what the system **must do**. They are the specific behaviors, features, and business rules that the application needs to execute.

- **The Focus:** Features, business logic, user interactions, and APIs.
- **The Impact:** If you miss a functional requirement, the software simply doesn't do its job (e.g., "The user must receive an email after signup").

### Non-Functional Requirements


These define how the system **must perform**. Also known as "Quality Attributes" (the "ilities": scalability, reliability, availability, latency).

- **The Focus:** Performance, security, capacity, and availability.
- **The Impact:** Missing a quality requirement can leave a system too slow, difficult to operate, or unable to handle the expected load.


> [!tip] Architectural Decision Record (ADR)
> An architectural decision record (ADR) can capture the requirement, options considered, and the reason for a decision. Both functional and quality requirements can influence application code and infrastructure.



> [!warning] The Availability Trap
> Set an availability target based on user needs and operational capacity. Higher targets usually require more redundancy, monitoring, and recovery work; the cost depends on the system.
