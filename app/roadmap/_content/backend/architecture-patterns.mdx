# Architecture Patterns

## Modular Monolith

A modular monolith keeps the application in one deployable unit while defining boundaries between business areas. It can be a practical starting point when the domain and scaling needs are still changing.

### The Concept

- **Single Deployment:** Everything runs in one process. You deploy one artifact. It is significantly easier to build, test, and release.
- **Strict Boundaries:** Code is organized by business domain (e.g., Billing, Users). Modules cannot directly access each other's databases; they must communicate through strictly defined internal APIs or interfaces.

### Why it's popular

- **Simplicity:** Easier to debug and test than microservices. There is no network latency between modules because communication is strictly in-memory.
- **Future Options:** Clear boundaries can make it easier to extract a service later, although data ownership and integration still require work.


> [!tip] Pro Tip: The 'Monolith First' Strategy
> Start with a Modular Monolith. It allows you to move fast while your domain boundaries are still fuzzy. Only split into Microservices when you have a clear technical reason (e.g., different scaling needs or team autonomy).







## Microservices

A distributed architecture where an application is composed of many small, independent, and loosely coupled services.

### The Concept

- **Independent Deployments:** The Billing team can deploy their service 10 times a day without coordinating with the Users team.
- **Decentralized Data:** Every microservice **MUST** own its own database. Services communicate over the network (HTTP, gRPC, or Pub/Sub).

### The Trade-offs


| Feature | Monolith | Microservices |
| --- | --- | --- |
| **Complexity** | Low | High |
| **Deployment** | Atomic (All or nothing) | Independent |
| **Data Consistency** | Strong (ACID) | Eventual (Sagas/2PC) |
| **Network Latency** | None (In-memory) | Significant (Over network) |



> [!warning] The Distributed Systems Tax
> Microservices dramatically increase operational complexity. Network calls can fail, requiring you to implement **retries**, **circuit breakers**, and **distributed tracing**.







## Serverless Architecture

An execution model where the cloud provider dynamically manages the allocation and provisioning of servers (e.g., AWS Lambda, Google Cloud Functions).

### The Concept

- **Event-Driven:** Code executes only in response to triggers (like an HTTP request, a file uploaded to S3, or a scheduled cron job).
- **Elastic Capacity:** Some function platforms can scale down when idle and add capacity as requests arrive. Billing and scaling limits vary by provider and configuration.

### Cold Starts & Use Cases

- **Cold Starts:** If a function hasn't been run recently, the cloud provider needs to spin up a container from scratch, causing a noticeable delay (latency) on the first request.
- **Best For:** Payment webhooks, daily report generation, image processing, and rapid prototyping without infrastructure overhead.


> [!info] Industry Insight
> Modern "Serverless" stacks like **Vercel** and **Netlify** use Edge Functions to minimize cold starts by running your code closer to the user in hundreds of global data centers.
