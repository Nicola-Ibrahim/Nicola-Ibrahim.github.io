## JWT Authentication

JSON Web Tokens (JWT) provide stateless, cryptographically secure user sessions for modern APIs. Instead of storing session IDs in a database, the server issues a signed token containing user claims.

### Why is it Stateless?

- **No Database Lookups:** The token contains the user's identity (Payload) and is mathematically signed (Signature). The server only needs its secret key to verify the token hasn't been tampered with.
- **Microservice Friendly:** Any backend service with the secret (or public key) can verify the user independently. You don't need a central Redis instance just to check if a user is logged in.

### JWT Anatomy
A JWT is composed of three parts separated by dots (`.`): `Header.Payload.Signature`.

```json
// Example Decoded Payload
{
  "sub": "1234567890",
  "name": "John Doe",
  "iat": 1516239022,
  "role": "admin"
}
```

#### What to Save in the Payload (Claims)
- **Standard Identifiers:** Usually, you store the user ID (`sub`), issue time (`iat`), and expiration time (`exp`).
- **Roles & Permissions:** Storing `role: "admin"` allows the backend to authorize actions instantly.


> [!danger] Security Warning
> The payload is merely **Base64 encoded, not encrypted**. Anyone who intercepts it can read the contents. **NEVER** store sensitive data like passwords, SSNs, or PII inside a JWT.


### Secure Storage
Where you store the token on the client determines your vulnerability to different attacks.


| Storage Method | Security Risk | Recommendation |
| --- | --- | --- |
| **LocalStorage** | High (XSS Vulnerable) | ❌ Avoid for sensitive sessions. |
| **HttpOnly Cookies** | Low (XSS Protected) | ✅ **Best Practice.** JavaScript cannot read it. |



> [!tip] Pro Tip: Refresh Tokens
> Use short-lived **Access Tokens** (15m) for requests and long-lived **Refresh Tokens** (7d) stored in HttpOnly cookies to maintain security without forcing users to log in constantly.


### The Revocation Problem
Because JWTs are purely stateless, you cannot easily "invalidate" them before they expire. 

- **The Problem:** If a user logs out, the physical token remains technically valid until `exp`.
- **The Fix:** Rely on short-lived access tokens, or maintain a fast **Deny List** in Redis for logged-out tokens (though this technically makes the system slightly stateful again).







## API Versioning Strategies

Choosing the right API versioning strategy is critical for avoiding breaking changes and maintaining backward compatibility.


| Strategy | Pattern | Best For | Verdict |
| --- | --- | --- | --- |
| **Global (URI)** | `/api/v1/users` | Small/Medium apps | Simple to manage and understand. |
| **Resource-Level** | `/api/users/v2` | Microservices | Teams can move independently. |
| **Header** | `Accept: v2+json` | Public APIs | Keeps URLs clean and RESTful. |



> [!info] Industry Insight
> **GitHub** and **Stripe** are famous for using Header-based versioning or custom Date-based headers to provide a seamless experience for developers while iterating on their platforms.
