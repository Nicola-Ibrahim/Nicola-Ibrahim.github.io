# API Design & Security

## Signed Tokens and Sessions

A JSON Web Token (JWT) carries a set of claims and can be signed so an API can verify who issued it and whether it was changed. A signed token is not encrypted: clients can read its payload. The application still needs a clear session and authorization policy.

### What an API Must Check

- **Signature and algorithm:** Accept only the algorithms and keys configured for the trusted issuer.
- **Issuer and audience:** Confirm that the token was issued by the expected service and intended for this API.
- **Time claims:** Check expiry and any not-before value.
- **Authorization:** Check the requested action against the current permissions. A role claim can become stale before the token expires.

```json
{
  "sub": "user-123",
  "iss": "https://auth.example.com",
  "aud": "portfolio-api",
  "exp": 1760000000
}
```

The payload should contain only the claims the receiver needs. Avoid passwords, secrets, and sensitive personal data.

### Storage and Revocation

Browser storage choices have different risks. JavaScript-accessible storage exposes tokens to injected scripts. An `HttpOnly` cookie limits that exposure, but cookie-based sessions need appropriate `SameSite`, `Secure`, and cross-site request protections. Choose a strategy for the application's threat model.

A signed token can remain valid until it expires unless the API checks a revocation mechanism. Short lifetimes, refresh-token rotation, a server-side session, or a denylist are possible tools; each adds operational trade-offs.

## API Versioning

Version an API when clients need time to migrate through a breaking contract change. The version can be part of the URL, a request header, or a dated contract. The choice matters less than documenting what changes, supporting an overlap period, and testing old clients.

| Approach | Example | Trade-off |
| --- | --- | --- |
| URL version | `/api/v2/users` | Easy to see and route; versions appear in resource URLs |
| Header version | `API-Version: 2` | Keeps URLs stable; less visible without request inspection |
| Date-based contract | `API-Version: 2026-01-01` | Records a precise contract point; requires clear change tracking |
