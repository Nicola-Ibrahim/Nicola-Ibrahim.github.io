# Cloud Compute Models

Cloud hosting is a choice about how much infrastructure a team wants to operate. A virtual machine, a managed application platform, and a function service can all run application code, but they place different responsibilities on the team.

| Model | Team manages | Useful when |
| --- | --- | --- |
| Virtual machine / IaaS | Operating system, runtime, deployment, and most scaling decisions | The application needs a specific runtime or more infrastructure control |
| Managed application platform | Application code, configuration, and service integrations | The team wants a simpler deployment and operations path |
| Functions / FaaS | Function code, triggers, configuration, and connected services | Work is event-driven or has variable demand |

## Virtual Machines

A virtual machine gives the team control over the operating system and runtime. Examples include AWS EC2 and a VPS from another provider. That control is useful for unusual dependencies or deployment requirements, but it also means planning for patches, monitoring, backups, and capacity.

### Operational Questions

- Who applies security updates and monitors the host?
- How will the application be deployed and rolled back?
- What happens when the instance or its region becomes unavailable?

## Managed Application Platforms

A managed platform handles parts of the hosting environment and gives developers a deployment interface. The exact boundary varies: a platform may manage the runtime and HTTPS while databases, background workers, or scaling settings remain separate concerns.

A platform can reduce setup work, but its limits, pricing, and supported runtimes still need to match the application. Check the current documentation for the specific provider before choosing one.

## Functions as a Service

Functions run in response to requests or events. AWS Lambda is one example. This model can fit scheduled jobs, event processing, or APIs with uneven traffic. It comes with service-specific limits on execution time, concurrency, and resources.

Cold starts can add latency when a new execution environment is created. The delay varies with the runtime and configuration, so measure the actual workload instead of assuming a fixed number. Costs can also include requests, execution, storage, data transfer, and connected services.

> [!tip] Choosing a Model
> Start with the application's runtime, traffic pattern, latency needs, and the team's operational capacity. Compare the full system cost and the work required to run it, not only the price of the compute unit.
