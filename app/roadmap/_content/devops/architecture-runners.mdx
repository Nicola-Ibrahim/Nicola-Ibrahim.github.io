<Topic 
  id="hosted-vs-self-hosted" 
  title="1. GitHub-hosted vs. Self-hosted Runners" 
  shortDesc="Where does your automation actually run?"
>
When GitHub Actions runs a job, it needs a physical computer (a Runner) to execute your scripts. You have two choices.

**1. GitHub-Hosted Runners**

- **How it works:** GitHub provides fresh, ephemeral Virtual Machines (Ubuntu, Windows, macOS). When the job finishes, the VM is immediately destroyed.
- **Pros/Cons:** Zero maintenance, completely free for public repos. However, they have limited CPU/RAM and cannot access your private corporate intranet (VPNs/VPCs).

**2. Self-Hosted Runners**

- **How it works:** You install the GitHub Runner agent on your own servers (like an AWS EC2 instance or an on-premise rack).
- **Pros/Cons:** You have total control over the hardware (e.g., attaching powerful GPUs for AI training) and they sit safely behind your corporate firewall. The downside is you are responsible for updating and securing the server.
</Topic>

<Topic 
  id="docker-container-jobs" 
  title="2. Running Jobs inside Docker Containers" 
  shortDesc="Ensuring absolute consistency using the container directive."
>
The classic developer problem: "The pipeline passes on GitHub, but the code fails in production." This happens because the GitHub Ubuntu runner might have different system libraries than your production server.

**The Container Solution**

- **The `container:` Directive:** Instead of running commands directly on the Ubuntu VM, you can instruct GitHub to pull a specific Docker image and run all steps *inside* that container.
- **Absolute Consistency:** If production runs `python:3.10-slim`, your CI pipeline runs inside the exact same `python:3.10-slim` image. No surprises.
- **Tooling Isolation:** Prevents conflicts. You don't need to install Python, Node, and Java on the host machine; the container brings exactly the tools it needs.
</Topic>
