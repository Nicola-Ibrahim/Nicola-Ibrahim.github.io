# Python CI/CD Pipelines

## Marketplace Actions: setup-python

Setting up programming languages manually using bash scripts (`apt-get install python3`) is slow and prone to breaking when OS mirrors go down.

## The setup-python Action
This official action instantly provisions exact Python versions using pre-compiled binaries cached by GitHub.

- **Matrix Testing:** easily test your code against multiple Python environments (3.9, 3.10, 3.11) simultaneously.
- **Dependency Caching:** built-in support for `pip`, `pipenv`, and `poetry`. With one flag, it automatically caches your downloaded packages to speed up future runs.

```yaml
- name: Set up Python
  uses: actions/setup-python@v5
  with:
    python-version: '3.11'
    cache: 'pip'
```


> [!tip] Speed Tip: Virtualenvs
> Always use a virtual environment in CI to avoid polluting the runner's global Python space. Tools like `poetry` or `pipenv` handle this automatically.







## Running Linters & Formatters

Running unit tests is computationally expensive. You don't want to waste 5 minutes running tests just to find a syntax error or an unused import.

## Code Quality Tools


| Tool | Type | Purpose |
| --- | --- | --- |
| **Black** | Formatter | Enforces a consistent coding style. |
| **Ruff** | Linter/Formatter | Written in Rust; replaces Flake8/Isort/Black. |
| **MyPy** | Type Checker | Catches type-related bugs before runtime. |


- **Fail Fast:** Place these steps as the very first items in your CI pipeline. If `black --check .` fails, the pipeline crashes instantly, saving CPU time.
- **The "Bad Guy" Strategy:** Using CI to enforce standards removes subjective arguments from Code Reviews—the pipeline becomes the objective referee.


> [!warning] Anti-Pattern: Ignoring Lints
> Never use `--ignore` flags unless absolutely necessary. A "noisy" lint report leads to developers ignoring actual bugs.







## Building & Pushing Docker Images

Once the code is tested and linted, it needs to be packaged into an immutable artifact that can be deployed anywhere.

## The Docker Workflow

- **Immutable Artifacts:** By packaging your code, dependencies, and OS into a container, you ensure that "it works on my machine" also means "it works in production."
- **Dynamic Tagging:** Never use the `latest` tag in CI. Instead, use the `github.sha` (the commit hash) as the image tag. This allows for instant rollbacks and clear audit trails.
- **GitHub Container Registry (GHCR):** The `docker/build-push-action` securely pushes the resulting image to GHCR, making it ready for Kubernetes or Cloud Run.


> [!info] Multi-Stage Builds
> Use **Multi-Stage builds** in your Dockerfile to keep production images tiny. Install build-tools in Stage 1, then copy only the compiled bytecode to Stage 2.
